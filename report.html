The finding

Oversampling pre-selects limit × oversampling candidates, so the matched uncompressed run is one walking a pool of the same size. Compared that way, uncompressed wins on recall at every pool size — the ordinary compression tradeoff, exactly as the docs describe it. The gap narrows as the pool grows, from 0.054 at 10 candidates to 0.0001 at 160.

So the question worth asking is not which is better at the same pool. It is what each costs to reach the recall you need, and there quantization wins by affording a much bigger pool per millisecond.

2.0x to 2.8x faster to any recall target on this dataset. This is a latency win, not a memory win: rescoring reads the original float vectors, so they stay resident and the 1-bit copy is stored in addition to them.

The mechanism the docs leave out

oversampling and hnsw_ef both control how many candidates a search considers, and no Qdrant page mentions them together. The quantization docs define oversampling without referencing hnsw_ef; the search-parameters docs define hnsw_ef as "number of neighbors to visit during search" without referencing oversampling. The only link is a negative rule in the qdrant-search-quality agent skill — "Set hnsw_ef lower than results requested (guaranteed bad recall)" — which, since oversampling raises the results requested to limit × oversampling, implies ef has to track it. 

graph walk width = max(hnsw_ef, limit × oversampling)
rescore set size = limit × oversampling

Where the two configurations below imply the same walk width, recall is identical to four decimals: 25 of 25 such rows across all four limits. Where ef=pool falls below the default and narrows the walk, it is worse: 15 of 15. No exceptions.

Two consequences. You cannot starve the pool by leaving hnsw_ef alone — the pool wins the max, so the skill's warning does not bite on this path; you can only starve it by explicitly setting ef below the default. And at small limits oversampling does something other than you would guess: from 1x to 8x at limit 10, recall climbs 0.9238 to 0.9931 while the graph walk never moves off 100. That gain is entirely from rescoring more of the candidates already found, which is also why latency there is nearly flat.

How it was measured

  • Grid. Follows the parameter sweep in Qdrant's OpenAI binary-quantization article — oversampling x rescore x limit, limits 10/20/50/100 — and adds latency percentiles plus an ef sweep on both the quantized and unquantized side.
  • Dataset. KShivendu/dbpedia-entities-openai-1M, DBpedia entity text embedded with OpenAI text-embedding-ada-002, 1536 dimensions. First 100,000 rows indexed, the next 1,000 held out as queries.
  • Ground truth. Exact KNN over the same collection (exact=true, quantization ignored), per Qdrant's documented ANN-recall method. Recall is the overlap of the approximate and exact id sets divided by the limit, averaged over 1,000 queries. Every target is reachable by construction, so this isolates index and quantization loss and says nothing about whether the embedding model retrieves the right thing.
  • Why sweep ef at all. Oversampling raises the candidate count the index has to walk, so binary quantization at 16x does much more graph work than an unquantized search at the default. Sweeping ef on the unquantized side, and repeating the whole oversampling range at a fixed ef, is what makes the comparison apples-to-apples.
  • The default ef is 100. Leaving hnsw_ef unset gives recall identical to four decimals to an explicit ef=100 at every limit, which is this collection's ef_construct. Qdrant's docs do not state the default; this is what it measures as.
  • Index. m=16, ef_construct=100, binary quantization with always_ram, original vectors in RAM. Green and fully indexed before any query is timed. Rescoring from disk is a different and much slower story, not measured here.
  • Timing. 1,000 sequential single queries per configuration over local gRPC, 200-query warmup, client-side wall clock, nothing else running on the host. Roughly 0.3 ms of every figure is client and transport overhead.
  • Noise floor. p95 carries about 0.2 to 0.3 ms of run-to-run variation, so a few cells break monotonicity. The frontier gaps quoted here are 1 to 3 ms. Use p50_ms from the CSVs if you need finer resolution.
